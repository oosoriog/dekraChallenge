# Rule 06 — Persistence: H2 In-Memory + Audit & Soft Delete

## Status: MANDATORY (Phase 3)

> **Renamed from `06-persistence-audit-soft-delete.md`.** The previous version forbade
> soft delete and audit fields. The current assessment scope **requires** lightweight
> soft delete and audit fields. PostgreSQL is NOT used; the database is **H2 in-memory**.

The assessment requires an **in-memory database**. This project uses **H2**.

> **Dependency gate:** `com.h2database:h2` is NOT in pom.xml yet. Adding it is part of
> the first build/test cycle that needs it (Phase 3, or earlier if Phase 1 codegen build
> verification requires it) and **requires approval**. PostgreSQL/Flyway/Testcontainers
> dependencies are present but must be **removed/replaced** (gated cleanup task).

---

## Approach

- **Database:** H2 in-memory (embedded, no external server needed).
- **ORM:** Spring Data JPA + Hibernate auto-DDL.
- **Schema management:** Auto-generated by Hibernate (`spring.jpa.hibernate.ddl-auto=create-drop` or `update`).
- **Flyway:** Removed — not used for this assessment (auto-DDL is sufficient for H2).
- **Console:** H2 console may be enabled for debugging (`spring.h2.console.enabled=true`).

- **Previous decision:** PostgreSQL required, H2 forbidden, Testcontainers mandatory,
  audit fields and soft delete forbidden.

## JPA Entity & Persistence Notes

- The Producto JPA entity lives in the persistence adapter (`ProductoJpaEntity`).
- The domain logic (tax calculation, validation) must NOT depend on JPA infrastructure;
  the **domain `Producto` is hand-written and JPA-free**.
- `precio` (base price) maps to a `BigDecimal` / SQL `DECIMAL`/`NUMERIC` column. Never `double`/`float`.
- **Persist only the base price.** Tax amount and final price are computed on read, never stored.
- `id` is a generated `Long` (identity strategy).

### Mandatory audit & soft-delete fields (on the JPA entity)

| Field | Type | Meaning |
|---|---|---|
| `deleted` | `boolean` | Soft-delete flag; default `false` |
| `createdAt` | timestamp | Set when the row is created |
| `updatedAt` | timestamp | Updated on each modification |
| `deletedAt` | timestamp (nullable) | Set when the product is soft-deleted |
| `deletedBy` | `String` (nullable until deleted) | Authenticated username that performed the delete (see rule 05) |

> Keep it lightweight: `createdAt`/`updatedAt` may use simple JPA lifecycle callbacks
> (`@PrePersist`/`@PreUpdate`) or Spring Data auditing (`@CreatedDate`/`@LastModifiedDate`).
> Do NOT introduce Envers, history tables or external audit frameworks.

---

## Soft Delete Behaviour (consumer-visible contract)

DELETE behaves as a deletion **from the API consumer perspective**, implemented as soft delete:

- `DELETE /productos/{id}` marks the row `deleted = true` (it does NOT physically remove it),
  and records `deletedAt = now` and `deletedBy = authenticated username`.
- `GET /productos` does NOT return soft-deleted products.
- The dynamic query / search endpoint does NOT return soft-deleted products.
- `GET /productos/{id}` returns **404** for a soft-deleted product.

> **Fallback:** If soft delete materially complicates implementation or testing, fall back
> to physical delete — but only after recording the trade-off as a decision/ADR. Soft
> delete is the default target.

---

## What NOT to Do

- Do NOT use PostgreSQL.
- Do NOT use Testcontainers (H2 is the real DB — no container needed).
- Do NOT use Flyway migrations (schema is auto-generated).
- Do NOT introduce Envers, audit frameworks, history tables or complex traceability.
- Do NOT physically delete rows (use soft delete; physical delete is a documented fallback only).
- Do NOT store tax amount or final price (persist only the base `precio`).
- Do NOT expose audit fields in `ProductoResponse` unless explicitly approved later.
